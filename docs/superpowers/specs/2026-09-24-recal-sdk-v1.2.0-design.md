# recal-sdk-js v1.2.0 — design

**Date:** 2026-09-24
**Repos:** `recal-sdk-js` (the release) and `recal-mono` (a prerequisite PR)
**Branch:** `release/v1.2.0`

## Why this release exists

`recal-mono`'s `staging` branch is about to be promoted to `main`. Two changes in it
reach the public `/v1` surface, and the published SDK (`recal-sdk@1.1.0`) handles
neither.

**1. `failedUsers`.** `GET /v1/organizations/{orgSlug}/calendar/busy` and
`GET /v1/organizations/{orgSlug}/scheduling` now return a **required** top-level
`failedUsers: FailedFreeBusyUser[]` beside `data`. A non-empty array means the answer is
partial — the users listed contributed no busy time and no slots. Before this change
those per-user failures were swallowed into empty results, so a partial answer was
indistinguishable from a complete one.

The SDK drops the field twice over: `unwrapResponse()` (`src/utils/response.ts:65`)
returns `response.data.data`, discarding every sibling key, and `types.gen.ts:509` still
types the 200 as `{ data: TimeRange[] }`. Regenerating the client alone does not fix
this.

**2. Renamed operation ids.** `hono-openapi` moved from `^1.1.0` to `^1.3.3` in the
dependency sweep, changing how it derives `operationId` for parameterised routes:
`getV1Users:userIdScheduling` became `getV1UsersByUserIdScheduling`. All 33 parameterised
operations are affected. HeyAPI names every generated function and type from the
`operationId`, and `src/types.ts` re-exports **51** of those names, so regenerating
renames a large part of the SDK's public type surface.

### What is *not* changing

Verified by diffing the deployed specs (`api.recal.dev` vs `api.staging.recal.dev`),
comparing every operation's parameters, request body, and 200 schema:

- No path was added, removed, or changed.
- No request parameter or body shape changed anywhere, in any operation.
- `403` and `429` were added to the user free/busy and both user scheduling routes
  (`502` was already documented); org busy swapped its documented `401`/`502` for `400`.
  The SDK's error path is generic (`unwrapResponse` → `RecalError`), so this is types-only.

## Decisions taken

| Decision | Choice | Note |
|---|---|---|
| Renamed generated types | Accept the rename; document it | Ships as 1.2.0 with a loud Upgrading section |
| `failedUsers` shape | `getBusyTimes` / `getScheduling` return `{ data, failedUsers }` | The only shape where a partial answer cannot read as complete |
| Sequencing | Build now against staging, hold the publish | Re-verified against prod before the tag |
| The bogus auto-`400` | Fix `recal-mono` first | So v1.2.0 generates from a correct spec |
| Operation ids | Pin them in `recal-mono` to 1.3.3's names | Makes the ids Recal's contract, not the library's default |

Both the rename and the `getBusyTimes` / `getScheduling` shape change are breaking under
a strict semver reading; 2.0.0 would be the literal call. Shipping as 1.2.0 is a
deliberate decision, taken on the grounds that the SDK is young and the renamed symbols
are generated names nobody should have pinned. The Upgrading section carries both.

## Hard constraint: v1.2.0 cannot run against today's production

`failedUsers` is **required** in the new schema, and `client.gen.ts:167` calls
`responseValidator` with no `try`/`catch`:

```js
if (opts.responseValidator) {
  await opts.responseValidator(data);
}
```

A client regenerated against the new spec therefore throws a raw `ZodError` out of
`organizations.getBusyTimes()` and `getScheduling()` when run against a deployment that
does not yet send the field. This gates the tag, and it gates CI too — `tests.yml` runs
the integration suite against a live `RECAL_URL`.

(For the same reason, today's published 1.1.0 is *not* broken by the promotion: Zod
strips unknown keys rather than rejecting them, and the validator's return value is
discarded. 1.1.0 keeps working against the new API, silently minus `failedUsers`.)

## Part 1 — prerequisite PR in `recal-mono`

One PR into `staging`, two commits, one file: `apps/api/src/router/extern/index.ts`.

### 1a. Document the validation error the API actually returns

`hono-openapi@1.3.3` auto-attaches a `400` to every validated route that does not declare
its own — 18 operations gained one, taking the total from 18 to 36 of 38. Its schema is
wrong: it documents `{ success: false, error: [], data: null }`, while `vHook`
(`apps/api/src/utils/route.utils.ts:119`) returns `{ data: null, error: string }`.

The library exposes `defaultValidationErrorResponse` on `openAPIRouteHandler`
(`boolean | ResponseObject`). Pass the real envelope:

```ts
defaultValidationErrorResponse: {
    description: 'Validation Error',
    content: errorContent,
},
```

Routes that declare their own `400` are untouched — the library skips them
(`!schema.responses['400']`). Disabling the response with `false` is the wrong fix: every
validated route genuinely can answer 400, so documenting it correctly beats not
documenting it.

### 1b. Pin the operation ids

The rename in §Why reached a published package through a semver-range bump that nobody
chose. `hono-openapi` accepts a global override — `defaultOptions.ALL.operationId`, of
type `string | ((route: RouterRoute) => string)` — so the ids become Recal's contract
rather than whatever the installed version derives.

Pin them to **1.3.3's current names**, reproducing its algorithm (`dist/index.js:35-47`):
method in lower case, then each path segment in PascalCase, with a parameter segment
contributing `By<Param>`. The emitted document is unchanged today; the point is that it
stays unchanged through the next bump.

Carries a JSDoc saying why it exists, since a function that reproduces a dependency's
default behaviour reads as redundant without one.

### Gates for Part 1

- Serve the spec locally, diff against the currently deployed staging spec, and confirm
  the **only** difference is the `400` block. A changed `operationId` means 1b's
  reimplementation is not faithful.
- Root `bun run lint:check` and `bun run type-check`; `apps/api` `bun run test`.
- Title: `bugfix(api): document the validation error the api actually returns`, with 1b
  as its own commit in the same PR.

Scope note: the internal spec (`apps/api/src/router/intern/index.ts`) has the same wrong
`400`, but no codegen consumer — `apps/dash` is typed through Hono RPC. Left alone.

## Part 2 — the SDK release

Worktree at `/Users/torbenkoehler/Developer/Recal/.worktrees/recal-sdk-js-v1.2.0`,
branch `release/v1.2.0` off `main`. Deliberately outside the repo, so the main checkout
stays clean and Biome never sees a nested root.

### 2a. Regenerate

```bash
RECAL_OPENAPI_URL=https://api.staging.recal.dev/v1/openapi.json bun run generate
```

Runs only **after** Part 1 is deployed to staging, so the `400` is already correct.

`bun run generate` has shipped non-compiling output before (see the v1.1.0 changelog), and
`openapi-ts.ts` already carries one repair — `restoreCalendarTransformerStub()`. The step
is not done until `bun run typecheck` is green, and any new repair goes in
`openapi-ts.ts`, never in a `.gen.ts` file.

### 2b. Follow the rename

Mechanical, and the blast radius is known: four generated files, the six service files,
and `src/types.ts`. No service logic changes here — imports and call sites only.

### 2c. Surface `failedUsers`

`organizations.getBusyTimes()` and `getScheduling()` return `{ data, failedUsers }`
instead of the bare payload. They are the only two methods affected.

Mechanism: `unwrapEnvelope()`, a sibling export in `src/utils/response.ts` performing the identical error
handling to `unwrapResponse` and returning `response.data` whole rather than
`response.data.data`. Two callers, no new layer, no change to the other twenty methods.

Export `FailedFreeBusyUser` from `src/types.ts`.

### 2d. Tests

- Update the four call sites in `tests/integrations/organizations.test.ts`, and assert
  `failedUsers` is present and an array.
- Add a unit test beside `tests/unit/multiUserSlots.test.ts` covering the new unwrap:
  `failedUsers` survives, and the error branch still throws `RecalError`. This is the
  half that can be proven without a live API.

### 2e. Release metadata

- `CHANGELOG.md`: a v1.2.0 entry in the established style (emoji headings, `⚠️ Upgrading`
  last). Upgrading covers both breaks — the renamed type exports, with the
  `GetV1Users…` → `GetV1UsersBy…` shape of the change, and the two org methods' new
  return shape.
- `package.json`: `1.2.0`.

## Part 3 — sequencing and gates

1. Part 1 lands in `recal-mono` `staging`.
2. Part 2 is built against the staging spec. PR `v1.2.0` opened into `main`, **held**.
3. `recal-mono` `staging` → `main` is promoted; production redeploys.
4. **Release gate**, in order:
   - Regenerate against `https://api.recal.dev/v1/openapi.json` and confirm a **zero
     diff** against what is on the branch. This is what proves the held branch matches
     what actually shipped.
   - `bun run typecheck`, `bun run check`, `bun test tests/unit`.
   - The live integration suite against production.
   - Merge and tag `v1.2.0`; `version-check` and trusted publishing take it from there.

### Risks

- **The promotion goes out before Part 1 lands.** Production then serves the wrong `400`,
  and step 4's zero-diff check fails. Recovery is cheap — regenerate from production and
  let the `400` fix ride the next promotion — but landing Part 1 first avoids it.
- **Regeneration produces non-compiling output.** Precedent exists. Contained by making
  `typecheck` the exit condition of 2a rather than a later step.
- **The live suite needs credentials** (`RECAL_TOKEN`, `RECAL_URL`, and the Google token
  pair for the OAuth tests). The org busy and scheduling tests are exactly the ones that
  fail if pointed at production before the promotion.

## Out of scope

- Renaming the SDK's public type surface away from generated names. Real, and the reason
  this break was possible, but a larger change that belongs in its own release.
- Making the generated response validation tolerant of newly-required server fields.
  Considered and rejected for this release: it weakens validation, and pinning the spec
  in Part 1 addresses the same class of surprise at the source.
- `apps/api`'s internal OpenAPI document.
